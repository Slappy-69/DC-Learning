# Open questions

Ordered by how much each answer changes the design. Each has a proposed default that the brief already uses, so building can start without an answer. Related assumptions are listed by ID (see `ASSUMPTIONS.md`).

| # | Question | Why it matters | Proposed default (used in BRIEF.md) | Related |
|---|---|---|---|---|
| 1 | **Is a two-tier model (representative-day screening for all options, 8760 verification for the shortlist) acceptable, or must every option be 8760?** | Determines whether the ≤ 500 ms update target is reachable. 8760 for 600 options would take tens of seconds in a browser | Two-tier, with a visible model badge on every figure and a deviation flag above 5 % | M1, change 4 |
| 2 | **Should options come from enumerating discrete design choices (C1–C20) with rule-based sizing, or from continuous sizing optimisation?** | Defines the core engine and what an "option" means | Enumeration with rule-based sizing, numeric sweeps for sizes. Above 2,000, Latin hypercube sampling as a visible run setting the user can switch off. Dominated options marked and shown; hiding them is a user view setting, off by default | M2, M3, change 3 |
| 3 | **What are the weighted axes, and is resilience a requirement (pass/fail) or a weight?** | Drives ranking, Pareto views and the plain-English summary | Axes: Cost 35, Carbon 25, Time-to-power 25, Deliverability 15 (indicative — unverified). Resilience and site fit are requirement checks with badges, not weights; the site-fit penalty in deliverability is off by default | M4, M5, M6 |
| 4 | **How deep should the site model go: 2D plan with heuristic auto-layout and manual editing, or full 3D with terrain and layout optimisation?** | Largest single effort item; drives the tech stack | 2D plan plus optional 2.5D extruded massing; flat site; greedy auto-layout; manual drag editing | P5, S1, S2 |
| 5 | **Are the indicative spatial defaults (footprints, heights, separations in BRIEF §6.3) acceptable as starting points, and does RED have in-house benchmarks to use instead?** | Site-fit statuses depend directly on them, and the building footprint dominates | Use §6.3 as confidence C placeholders; replace with RED benchmarks and verified sources before release | S3, S4, S7 |
| 6 | **What capex scope should options be compared on: energy and backup plant plus cooling delta only, or full project capex including the data hall?** | Affects how clients read the numbers and whether cooling choice can be fairly compared | Differences only: energy, backup, grid connection, substation, plus cooling capex delta. Building and IT excluded and stated in every output | M8 |
| 7 | **What should the default resilience requirement be?** | Sets backup unit counts and fuel storage on every option, which takes a lot of land | 100 % IT + essential mechanical backed, N+1, 48 h autonomy, 5 min UPS (indicative — unverified); Tier label optional and for reference only | M7 |
| 8 | **Who is the target user in practice: internal RED engineers only, or also clients using it themselves?** | Changes the onboarding, default complexity and whether presentation mode is key | Engineer-operated, client-facing in workshops; presentation mode and exports for clients | P1 |
| 9 | **How should permitting thresholds be handled across countries?** | Permitting flags feed deliverability. National rules differ (e.g. UK, Ireland, Netherlands, Nordics) | EU IED and MCPD thresholds for every built-in country, with no national variation built in; editable per project; non-EU countries flagged "EU threshold used as a proxy"; national packs later | D4 |
| 10 | **Do location-specific (not country-level) solar, wind and temperature profiles need to ship built-in?** | Accuracy in large or climatically varied countries, and data size | Country-level built-in; location-specific by user CSV upload (with in-browser clustering) | D1 |
| 11 | **Should the tool rank requirement-compliant options first by default?** | Tension between "flag, never enforce" and showing a non-compliant option as the leader | Off by default (flag-not-enforce), with a visible toggle that is recorded in exports | change 5 |
| 12 | **Is a template-based plain-English summary acceptable, or should it use a language model?** | Determinism, offline use and testability vs richer wording | Templates, deterministic, user-editable | Q4 |
| 13 | **Must the tool model AI-training load transients and their effect on BESS, UPS and grid?** | Increasingly important for AI campuses; significantly more modelling | Not modelled; flag on AI training workload type | M15 |
| 14 | **Which exports matter most for handover: PDF/Excel only, or also GeoJSON/DXF/IFC for architects and Forma-type tools?** | Integration with the wider design workflow | PDF, Excel, project JSON, GeoJSON, PNG/SVG. DXF/IFC out of scope | §22 |
| 15 | **Should the default grid-date uncertainty be asymmetric (−6/+24 months)?** | Strongly influences time-to-power ranges and whether bridging options become the robust pick | Yes, −6/+24 months, editable; indicative — unverified (no source) | M12 |
| 16 | **In dispatch, should the stated grid capacity be modelled as given (demand above it shown as flagged unmet load) or allowed to be exceeded and flagged?** | Changes unmet-load results and how grid-constrained options look | "Show unmet load" by default (renamed from "Physical limit" in revision 3; modelling the input as given, not enforcement, per BRIEF §2 principle 5), with "Show exceedance" selectable; both flagged, neither hides, demotes or resizes options (BRIEF §9.4) | M17 |
| 17 | **Should "Hide dominated options" default to off?** | Off keeps the brief's flag-not-enforce principle literal but shows long lists; on gives shorter lists at the cost of a default hide | Off; one click to turn on, state shown in header and exports (BRIEF §7.2 step 6) | M3 |
| 18 | **Should the grid connection on each option be the full offered capacity, or should options be allowed a smaller contracted capacity?** | Changes grid connection capex and how grid-heavy and on-site-heavy options compare | Full offered capacity for every grid-using option, never resized by the tool; shortfall shown and dispatched as unmet load; smaller contracted capacity only as a user size override on a custom option (BRIEF §9.2) | M23 |
