# Build notes: core slice

Concept-stage data centre energy optioneering tool, core slice, built against `brief-v2/BRIEF.md` (authoritative), `ASSUMPTIONS.md`, `OPEN-QUESTIONS.md` and `CHANGELOG.md`. Built 2026-10-15.

## Decisions for the owner

Two points are open. The build uses the current default for both, and neither has been decided for you.

**(a) A no-backup option whose on-site plant meets every resilience item.** This is an option with C5 = None (no designated backup) whose retained bridging or firm prime plant still covers backed load, topology, autonomy and islanding. On the test-3 sample there are three: islanded gas recip, fuel cell and rented plant, at 137 to 140 MW against 127.7 MW critical load.
- *Current default: "Does not meet".* The failing item is named "Backup technology: none selected (C5 = None)". This follows §8, which says "None (flagged)", and treats plant that is not designated as backup as not counting.
- *Alternative: "Meets with flags".* The option passes on the §9.7 items, because §9.7 counts retained and prime plant as backed load, and it carries a "no designated backup" flag.
- Where it applies: `resilience` in `src/engine/evaluate.js` (the `v.C5 === 'none'` item). It has no effect on T1 or T3 at defaults, because C5 = None is not generated by default.

**(b) Whether options may contract less grid capacity than the offer (OPEN-QUESTIONS 18).**
- *Current default:* every option uses the full offered connection (the same per-month profile, never resized) and pays the same grid connection cost. Any shortfall is dispatched as unmet load and flagged. Test 2 checks this.
- *Alternative:* options may contract a smaller capacity, with lower connection capex and possibly lower standing charges. On-site-heavy options would then compare more favourably with grid-heavy ones. This needs a sizing rule for the contracted capacity, or a per-option choice, plus a connection cost that scales with capacity. The brief currently allows a smaller capacity only as a user size override on a custom option (§9.2), which is not built in this slice.

## How to run

```
cd /home/claude/build/app
npm install          # react 18.3.1, react-dom 18.3.1, esbuild 0.23.1 (all local to this folder)
npm test             # node tests/run-tests.mjs
npm run build        # node build.mjs -> dist/
npm run test:browser # node tests/browser-tests.mjs: Playwright + Chromium + axe-core on dist/energy-tool-single-file.html
                     # (run the build first; prints SKIP and exits 0 when Playwright or Chromium is not available)
```

Open `dist/index.html` through any static server (for example `npx serve dist`). The compute pool uses Web Workers loaded from `worker.js`. If workers cannot be used, the app falls back to the main thread and says so in the status line. This covers a synchronous failure (the `Worker` constructor throws, as some browsers do on `file://`) and an asynchronous one (`worker.js` fails to load or throws, or a message cannot be read: `worker.onerror` / `worker.onmessageerror`). In the asynchronous case every worker is terminated first and the status line reads "Worker failed: workers terminated, running on the main thread instead." Two more paths fall back the same way: a `postMessage` to a worker that throws ("Worker could not be started") and a worker that goes silent with no error event, for example killed by the browser ("Worker stopped responding"). A watchdog catches the silent case: no message from a worker that has not yet returned its result for 30 s. While working, a worker sends events at least every 0.55 s on T1. An engine error reported by a worker ends the run with the error shown; it is not retried on the main thread, which would fail the same way.

`dist/energy-tool-single-file.html` is the same app with `app.css`, `app.js` and the worker inlined, built by `npm run build`. The worker source (`dist/worker.js`) is embedded as a string and the workers are created from a Blob URL (`URL.createObjectURL(new Blob([src], { type: 'text/javascript' }))`), so the file loads no other file and can be opened from a download, including on a phone. The page contains no `<script src>`, no `<link href>` and no relative file reference (checked by test 7). If the browser refuses Blob workers, the same fallback applies. The fallback runs in 30 ms time slices, so the page and the progress panel stay live. Checked in headless Chromium 2026-10-15: the single file from `file://` runs on a Blob worker and requests only itself and the `blob:` URL; the normal build with `worker.js` missing falls back on `file://` (constructor throws) and over HTTP (404, asynchronous `onerror`), and both runs complete.

Data flow: inputs (UI keeps `null` for "at default" on derived defaults) → `normalizeInputs` → `buildContext` (with the site model) → `generateOptions` → per option `sizeOption` → `buildBlocks` → layout (batched, cached by block-set key; "fill residual" solar sized from it) → site fit → `dispatchConfig` → `dispatchAll` (cached by configuration key, so options that differ only in non-dispatch choices share one dispatch) → `timeToPower`, `economics`, `carbon`, `resilience`, `optionFlags`, `deliverability` → `scoreOptions` over the whole screened set → `applyView` for display only.

Incremental recompute: a change to weights, cost/carbon axis metric or "rank compliant first" re-scores the existing run on the main thread with no dispatch. Any other input change re-runs the pipeline in the worker pool; in-flight workers are terminated first.

## What is implemented

**Input model.** All §5 inputs needed by the engine, with the brief's defaults. Required inputs (location, site area, IT MW, grid now, grid at full connection, full-connection date) have no default; the app pre-fills the T1 reference example so it runs on load and marks those fields "required · example value". The Inputs panel covers steps 1 to 6 plus run and dispatch settings, with the label rule applied (see below).

**Hourly profiles (synthetic).** For each of the 31 built-in countries, `profiles.js` generates seeded, deterministic 8760-h arrays: dry-bulb and wet-bulb temperature, solar yield per MWp, wind capacity factor, wholesale price and grid carbon intensity. They are scaled exactly to the indicative annual targets in `COUNTRIES`, which are themselves indicative and unverified. **These are synthetic profiles, not measured data.** The UI says "Synthetic profile (seeded), calibrated to indicative annual targets — not measured data". No dataset licence has been checked yet. Price and carbon are anti-correlated with wind and solar and follow seasonal and diurnal shapes.

**Dispatch (real, 8760 h).** `dispatch.js` runs the six-step merit order from §9.4 hour by hour over full 8760-hour model years, carrying BESS state of charge from year to year:
1. On-site solar and wind serve load first.
2. PPA energy is shaped hourly (solar, wind, hybrid, baseload or demand-shaped 24/7), delivered over the grid connection, and uses import capacity. PPA volume that cannot be delivered is settled at spot and flagged.
3. BESS discharge depends on its role. Peak-shave covers the shortfall above grid plus firm capacity, then expensive hours with a 50 % reserve. Shifting and grid services discharge in the n dearest hours of each day. Bridging support covers shortfalls only. BESS charges from on-site surplus first, then from the grid in the n cheapest hours of each day, within the import cap.
4. Firm plant runs when its marginal cost (fuel ÷ efficiency + VOM + carbon) is below the hourly grid price, or to cover the gap above grid capacity. Min stable load is respected per unit, and output forced above need by min stable load is curtailed. Plant is must-run when islanded. The trigeneration absorption-chiller credit is limited to the mechanical cooling load in that hour. Run-hour handling follows the setting ("Flag only" or "Respect limit").
5. Grid import is capped at the offered capacity for that month ("Show unmet load"), or uncapped with the excess recorded and flagged ("Show exceedance").
6. Demand flexibility runs if C16 is on. Anything still unserved is recorded as unmet load.

Each hour is checked for balance inside the engine (`maxBalanceError`). Model years are dispatched explicitly up to the last change in demand, grid or plant availability (capped at 8 years, a run setting). The last year then repeats as steady state over the evaluation period.

**Option generator.** This is the Cartesian product of open choices (locked choices give one value). Irrelevant choices collapse to "n/a" (rule d). Compatibility rules (a), (b), (c) and one builder rule (e) remove impossible combinations, and each is counted. All 11 archetype baselines (A1 to A9, A10a SMR, A10b hydrogen) are always generated, and so are archetype vectors that sit outside the open choices. When the count exceeds the cap (2,000) and "Sample above cap" is on, every archetype is kept, then seeded Latin hypercube sampling runs over the choice dimensions. Draws that land on an invalid or duplicate combination are repaired from the remaining valid set, and the number repaired is reported. Switching sampling off screens every combination. The "values not generated" note lists every omitted value with its reason ("default subset", "locked", "wind default", "excluded by user") and an Include control. The C11 wind info flag shows on the C11 row and in the run summary.

With brief defaults on T1, the open choices give 57,024 valid combinations (57,028 with the 4 archetypes that sit outside the open choices), so sampling is active on a default run. See "Brief issues" (1).

**Sizing.** §9.2 rules with sentences:
- Design load is built from the peak design-day PUE.
- Critical load drives backup unit counts, using the block rule for N, N+1, 2N and catcher.
- Fuel storage is sized from autonomy.
- Bridging is sized to the largest shortfall, using N+1 per block.
- Firm prime is sized to the steady-state average.
- BESS is sized as a percentage of design load, kept as given.
- Roof, carport and residual-ground PV use an area budget.
- Wind count comes from spacing.
- The PPA volume is reported.
- The grid connection is the offered capacity per period, the same shared array for every option, never resized. The grid shortfall at design load is stated per period.

**Economics.** One real-terms cash-flow ledger per option, the source for LCOE, NPV of net cost, capex and opex.
- Capex is timed by phase (C19), with contingency, replacements, and residual value at the end of the period or salvage on removal. The cooling capex delta is relative to the air baseline.
- Opex covers fixed O&M, VOM, fuel, grid energy plus the non-commodity adder (also charged on PPA energy carried over the grid), PPA strike plus shaping, Scope 1 carbon cost, genset test runs, rental for rented bridging plant, and export revenue.
- Capex scope excludes the data hall shell and IT fit-out, stated in the UI.

**Carbon and water.** Location-based and market-based annual average gCO₂e/kWh with the decarbonisation trajectory, hourly CFE %, the Scope 1/2 split, a trajectory per year, and WUE.

**Resilience check.** Backed load (backup at topology after removing redundant units, plus retained bridging, firm prime and BESS), topology against the requirement, autonomy, islanding if required, and gas dependency. Status is Meets, Meets with flags or Does not meet, with the failing item named.

**Time-to-power.** For each month, supply = offered grid + firm plant available (programme and fuel dates) + bridging BESS. The tool reports first power, full load, power gap in MW-months, and the axis metric (months to full load + 0.5 × power gap ÷ design MW). The phase targets drive the "target missed" flag.

**Flags.** §15 categories: grid, resilience, permitting (IED, MCP, Seveso fuel and hydrogen, wind, stack height, run-hours; non-EU proxy note; "Screening flag, not a permitting determination"), fuel and utilities, targets and ceilings, technology, generation, data, load, and an area-budget info flag. Flags never remove, hide, demote or resize an option.

**Deliverability.** §9.9 formula: Emerging and Nascent shares (mean of capacity and energy shares), permitting major and minor counts, gas "Unknown", hydrogen, and procurement lead time over 24 months. Floored at 0. The site-fit penalty is off and has no effect because site fit is not assessed.

**Scoring.**
- Effective weights are raw ÷ Σ raw, with equal weights and a notice when all are 0.
- Each axis is normalised 0–100 across all screened options (best = 100).
- The weighted score is Σ wᵢ·scoreᵢ.
- Dominance is marked on (cost, carbon, TTP, deliverability) with no better resilience status.
- Ranking is by score. "Rank requirement-compliant options first" is off by default.
- View filters (resilience status, show only with flag, hide with flag, capex ceiling, dominated status, archetypes only, search, hide dominated, sort) are applied after scoring by a pure function and never change any score or rank. Each active filter is a removable chip on both result tabs. The land-take ceiling filter waits for the site slice (Brief issue 13).

**UI.**
- The header strip shows option counts (shown, screened, combinations, dominated), leader and score, model badge, sampling and hide-dominated state, filter count, exceedance-mode warning, effective weights, and the unverified-defaults count (all records; the count affecting the leader is not available yet, Brief issue 16). The leader is `weightedPick()`, the same function as the Trade-offs pick.
- A polite live region announces "Options updated. Leader unchanged" or "New leader: …".
- The run summary sits above the list and expands automatically when an entry changes.
- The ranked table is sortable, paged at 50 rows, with axis mini-bars, badges and flag counts. An option detail row shows scores, economics, energy, time-to-power, resilience, deliverability, sizing sentences, flags and the choice vector.
- The layout is responsive: a sliding inputs panel below 1280 px and single-column fields below 768 px.
- All controls are native and keyboard-operable, with a visible focus ring, skip links ("Skip to results", "Skip to trade-offs chart"), `prefers-reduced-motion` support and dark mode. Text meets 4.5:1 and form-control boundaries 3:1 in both themes. The "indicative — unverified" tags are not tab stops; their basis is the described control's accessible description. Below 1280 px the closed inputs panel is hidden from focus.
- No browser storage APIs are used.

## Brief issues

1. **Default option count conflicts with §7.2 and §17.** The brief says default open choices give "about 200–600 options" and the cap "is only reached when the user opens extra choices". The §8 default states alone multiply far beyond that. C1 bridge × C2 (3) × C3 (4), C4 (3), C5 (3), C8 (4), C9 (3), C10 (3), C12 (3), C13/C14 (1 + 3) give 57,024 valid combinations on T1 even after n/a collapse. **Choice made:** follow the §8 default states literally and let the visible "Sample above cap" setting (default On) screen 2,000 with every archetype kept. The run summary and header strip state the real counts. The brief should either shrink the default open sets (for example lock C3, C9 and C14 by default) or revise the 200–600 figure and the §17 targets.
2. **§17 timing targets assume the representative-day tier.** This slice runs the full 8760-h dispatch for every option, as the task requires. On this sandbox, T1 (2,000 options, 1,700+ distinct dispatch configurations, about 10,000 dispatched 8760-h years) takes several seconds on one thread. In the browser it is divided across the worker pool. The ≤ 500 ms / 1.0 s targets are not met in this slice. They depend on the representative-day screening tier (§9.1), which is not built yet.
3. **C5 "Retained bridging plant" without retained plant.** The brief lists no compatibility rule for C5 = retained when C1 = wait (no bridging plant exists) or C1 = bridge with C3 = remove. Such a combination cannot be described: the backup technology is plant that does not exist. **Choice made:** added rule (e) "Retained-bridging backup requires retained bridging plant", shown by name with its count (5,184 on T1). Possible but weak combinations stay generated and flagged.
4. **Retained bridging as backup: sizing basis.** §9.2 sizes bridging to the grid shortfall, which can be far below the critical load (6.6 MW against 103 MW on T1). That makes every "retained as backup" option fail resilience by construction. **Choice made:** when C5 = retained, the retained plant is sized by the same backup rule (critical load, required topology, autonomy for liquid fuel), taking the larger of the two sizes. This is a sizing rule applied to every such option before any check (§2 principle 5), not a resize after a breach.
5. **Islanded grid as backup in the resilience check.** C1 = Islanded keeps the offered grid connection "as backup". The §9.7 resilience check counts only on-site firm capacity during a grid outage. **Choice made:** the islanded grid connection is not counted toward backed load.
6. **"BESS role" is not a separate choice in §8.** C12 combines size and role. The default role is fixed as "peak-shave against grid cap". **Choice made:** modelled as a separate choice row C12r (locked to peak-shave by default), so rule (c) "BESS as bridging requires a non-zero BESS size" has something to act on.
7. **C12 alternatives.** The brief gives durations 1/2/4 h at 25 %/50 % but only three defaults. **Choice made:** six size alternatives plus None; the defaults are None, 2 h at 25 % and 4 h at 50 %.
8. **Phase dates for T1** are not given (§21). **Choice made:** months 18, 30, 42 and 54 from the analysis start.
9. **Time-to-power metric when full load is never reached.** The brief's formula needs "months to full load". **Choice made:** use the timeline horizon (120 months, a run setting) when full load is not reached in it, plus the power-gap term.
10. **"Supply ≥ demand at the required resilience" for first power** (§9.8) is not defined further. **Choice made:** first and full power test the energy supply only (grid + firm + bridging BESS). Resilience is reported separately by the resilience check.
11. **Deliverability maturity share**: "energy-weighted and capacity-weighted" with one penalty. **Choice made:** the mean of the capacity share and the steady-state energy share.
12. **AC5 "weighted leader" is not defined** (Pareto review, 2026-10-16). AC5 says "the highlighted Pareto pick and the plain-English summary always match the weighted leader". The brief never defines "weighted leader". Ranking is "by weighted score" (§11), but "Rank requirement-compliant options first" (§11 (b)) can put a lower-scoring option at rank 1, and the header calls rank 1 the "leader" (§12). **Interpretation (owner's decision, applied):** the weighted leader is rank 1 under the current weights and ranking settings. The highlighted pick, the header "Leader", the live "New leader" announcement and, when it is built, the plain-English summary all use one function, `weightedPick()` in `src/engine/pareto.js`, so they always name the same option. With the toggle off (default) rank 1 is also the highest weighted score. With it on, the highest-weighted-score option can be a "Does not meet" option ranked lower. It is then marked separately: a dashed ring with "Highest score #k" on the chart, a "Highest weighted score" badge in the table, and a pick-line sentence giving its rank and the reason (the toggle is on and its resilience status is "Does not meet"). Test 8g checks this on synthetic and real options. (The slice first kept the pick on the highest weighted score; its note cited "§11 wording", but the wording is AC5's, not §11's.)
13. **Land-take ceiling view filter** (§11, §2 principle 5) needs land take per option, which comes from the site model (§10). **Choice made:** deferred to the site slice and listed under "What is not in this slice". The other §11 filters have controls: resilience status, show only or hide options with a flag, capex ceiling, dominated status, archetypes, search and "Hide dominated options". ## Run event log (trackability)

Added 2026-10-15. Every run, in the worker pool or on the main thread, emits an ordered event log. The engine is in `src/engine/runlog.js` and `src/engine/run.js`, the UI in `src/components/RunProgress.jsx`.

### Event schema

Each event is a plain object, and the field order is fixed:

```
{ seq, stage, event, t_ms, count, total, detail }
```

| Field | Meaning |
|---|---|
| `seq` | Contiguous integer from 0 within a log. In a merged pool log it is renumbered 0..N−1, and the source's own number is kept as `detail.wseq`. |
| `stage` | One of the 12 stage ids below, in pipeline order. |
| `event` | `start`, `progress`, `end` or `warning`. |
| `t_ms` | Milliseconds since the run started, at 1 µs resolution. Workers use the same origin: the main thread passes its absolute start time (`performance.timeOrigin + performance.now()`). **This is the only field that differs between two runs with the same inputs.** |
| `count` | Items processed so far. `start` gives 0, `end` gives the items processed in the stage, `warning` gives null. |
| `total` | Items expected in this stage for this source, or null when not known in advance (option generation start). |
| `detail` | Plain object. It always has `source` (`main` or `worker k`). On `end` it always has `items`, `cacheHits`, `cacheMisses` (null when the stage has no cache) and `warnings` (the number of warning events the source raised in that stage). It never holds timings or anything else machine-dependent. |

Log content is deterministic. Progress for per-option stages is emitted every `PROGRESS_EVERY` = 250 items, counted, not timed. Dispatch reports every option. The input hash is computed on the normalised inputs with sorted keys, so it does not depend on key order. Test 6b checks that two T1 runs give identical logs once `t_ms` is removed.

### What each stage reports

Stages run as passes over the option list, in this order. Each source has exactly one `start` and one `end` per stage it runs. Per-option results are unchanged: T1 and T3 outputs for all 2 × 2,000 options (ids, scores, ranks, LCOE, NPV, capex, carbon, unmet, time-to-power, deliverability, resilience status, flag ids, dominance, dispatch keys) were compared before and after the restructure, and they are byte-identical.

Warnings record run-level conditions. Per-option conditions stay as flags on the options, and the log counts them; it does not list each one.

### Worker pool and fallback

- **Pool.** The main thread runs stage 1 as a coordinator (source `main`), which gives the input hash. Each worker runs stages 1 to 11 on its slice with its own logger (source `worker k`, own `seq` from 0) and returns the log with its result. For the live panel it also streams copies of its events in batches (every 200 events or 120 ms); test 6c checks the streamed copies equal the returned log. `mergeRuns` runs stage 12 on main and merges with `mergeLogs`: order by stage, then source (main, worker 0, worker 1, …), then the source's own `seq`, renumbered 0..N−1. Within a source the order is that source's sequence order. The merged log never goes backwards in stage order.
- **Main-thread fallback.** `runModelSteps` is a generator that yields between work items. The fallback drains it in 30 ms slices with `setTimeout(0)` between them, so the progress panel updates during the run. The log content is identical to the synchronous run (test 6d).
- **Cancelled or failed runs.** Events received so far are kept per source. "Download run log" then exports a partial log, merged the same way, with `_partial` in the file name and `status: partial` in the JSON header.

Worker slices are taken by index (every k-th option). Options that share a dispatch configuration can land in different workers, and each worker's cache is local. On T1 with 3 workers, 185 of 1,732 configurations are simulated in more than one worker. The merge step reports this (`duplicatedAcrossWorkers`). Results are unaffected; it only costs time. Slicing by configuration key would remove it, but it is not done here.

### UI

- **Run progress panel** (above the run summary, open by default): headline (current stage and percent, event count, warnings), one row per stage with percent complete, a bar, cache hit/miss and warning count, and a scrolling log of the last 200 events. The log follows the newest event until the user scrolls up; a "Follow latest events" control resumes following. On a phone (below 768 px) stages are one column, and each log line wraps under its timestamp, source and stage. There is no horizontal scroll at 390 px (checked headless).
- **Percent per stage** is the mean over the sources expected to run it: workers for stages 1 to 11, main for stage 12. In the pool, stage 1 also runs on main, and the panel shows the workers' share.
- **Accessibility.** One polite, atomic live region announces the current stage only, when it changes, for example "Run in progress: Dispatch (8760 h), stage 5 of 12.", then "Run complete. All stages finished." The event log is `role="log"` with `aria-live="off"`, so individual events are not announced. The status line spinner text is `aria-hidden` while running, so the stage is not announced twice.
- **Download run log**: JSON and CSV buttons. File names are `run-log_<inputHash>_<YYYYMMDD-HHMMSSZ>.json|csv`, plus `_partial` for an unfinished run. The JSON has a header (`schema: dc-energy-run-log/1`, input hash, engine version, mode, run start and export time, validation result, stage list, field list, event count) and then one event per line. The CSV has one row per event, columns in schema order, with `detail` as a quoted JSON string.

Size: a T1 log is 2,086 events (single thread) or 2,089 to 2,155 (pool, depending on worker count), about 1.3 MB as JSON. The UI holds the full log only in the finished run object; the panel keeps 200 events.

### What was built

- **`src/engine/pareto.js`** (pure, no UI). This is `HOOKS.paretoView(run, axes, view)`. It reads the scores, ranks and `dominatedBy` marks that `scoreOptions` has already written, and returns a view model: visible points, the 2-axis frontier, the weighted pick, time-to-power colour classes and the capex range. Helpers: `paretoFrontier` (O(n log n), both axes minimised, exact ties do not dominate each other; higher-is-better axes are negated first), `weightedPick` (rank 1, the weighted leader; Brief issue 12), `highestWeightedScore` (ties broken by id as in `rankOptions`; marked separately only when it is not rank 1), `paretoTableRows`, `PARETO_AXES` and `defaultParetoAxes`.
- **Two kinds of "dominated", kept apart.** The engine's dominance mark (§7.2 step 6: all four axes plus status) shows as a **hollow** marker. The frontier on the chart is the 2-axis Pareto set for the plotted pair, drawn as a dashed step line. Both are computed over the whole scoring set, so view filters and "Hide dominated options" never move the frontier or the pick (§11 scoring scope).
- **Axes (any two, §12.2).** X and Y can each be any of seven axis metrics: LCOE, NPV of net cost, carbon (location-based, market-based, 1 − hourly CFE), time-to-power and deliverability (higher is better; Brief issue 15). By default the axes follow the scoring Cost and Carbon metrics (records `view.pareto.xAxis` / `yAxis` = "follow-scoring"). "Reset to default axes" restores them. The axis choice is view state, not an input, so changing it never triggers a run. (Before the review only cost × carbon could be plotted, although this note already said "any pair".)
- **Encodings (§12.2).** Colour = time-to-power. Size = capex (marker area grows linearly with capex from a minimum mark: radius 3–9 px, 2.5–7 px on phones; earlier wording "proportional" was not accurate). Shape = **resilience status** (circle Meets, triangle Meets with flags, square Does not meet), because site fit is not assessed yet (see open points). Weighted pick (rank 1) = orange double ring plus the text label "Weighted pick #1". The table row is highlighted, and a pick line above the chart names the option and its two axis values. ### Palette decision

The code has **no energy-source colour system** yet. There is no technology colour token in `defaults.js` and no source colours in `styles.css`. The §16 signature palette belongs to the dispatch stacks and site blocks, which are later slices. This chart encodes time-to-power (a magnitude), not energy source, so a source palette would be the wrong tool here anyway. Choices made:

- **Time-to-power: one-hue violet ordinal ramp, 5 steps** (hollow, dominated markers are stroked at full opacity: at the earlier 0.75 opacity the lightest step fell to 2.5:1 light / 2.7:1 dark). Light theme `#9d74c4 #8659b0 #70429b #592f83 #421c69`. Dark theme `#9466bf #a97fcf #bf9bde #d4b9ec #eadcf8`, so in both themes more contrast with the surface means a longer time-to-power. Violet carries on from the existing `--ax-ttp` axis colour (`#8a4fa3`) in the ranking table, so time-to-power reads as violet throughout the app. Both ramps were run through the dataviz palette validator in `--ordinal` mode against the real surfaces (`#ffffff` and `#1e2125`). All checks pass: monotone lightness, adjacent ΔL ≥ 0.06, single hue (spread 2–4°), and the end nearest the surface at 3.67:1 (light) and 3.78:1 (dark), so every marker clears the 3:1 graphics target. A single hue is colour-blind safe by construction, because the classes differ in lightness, not hue.
- **Quantile classes, with ties merged.** Time-to-power on T1 is heavily clustered (the 2nd and 50th percentiles are 18 and 24 months). Tied quantile edges are merged, so T1 shows 4 classes spread across the ramp, and the legend prints each class's month range.
- **Pick and focus.** The pick ring uses the existing `--focus` orange (`#b4560a` light, `#ffb366` dark), which is separate from the violet ramp and from the status colours. The pick always has a text label too, never colour alone. Focus and selection rings use `--focus` and `--accent`.
- **Status colours stay reserved.** Resilience status uses shape plus a text legend, not the ok/warn/bad colours, so status colours are never reused as a data encoding (§16). Dominated is shown by fill (hollow or solid), which also survives greyscale and forced colours.

### Chart library decision

**Hand-written SVG (plus Canvas above 500 points). Recharts was not added.** The weight was measured: a minimal Recharts 2.15.4 import (ScatterChart, Scatter, axes, ZAxis, Tooltip, Line, grid, ResponsiveContainer) bundles to **112 KB gzipped** on top of React, which is more than the whole current app (`dist/app.js` is 109 KB gzipped after this slice). It also pulls in about 30 packages (d3 modules, lodash and others), and every one of them lands in the single-file build. The JS budget (≤ 1.5 MB gzipped) would still be met, so weight alone is not decisive. The deciding reasons are functional:
1. §4 requires Canvas above 500 points. Recharts renders SVG only, so T1's 2,000 points would need a custom Canvas layer anyway, and Recharts would end up drawing only the axes.
2. The keyboard model (arrow keys between points, P for the pick, Enter to open) and the nearest-point hit area would have to be built on top of Recharts' tooltip model, which works by mouse hover.
3. Tests 8d render the real chart with `react-dom/server` and match every plotted point to a table row. Recharts' `ResponsiveContainer` renders nothing without a measured DOM size, so that test would need a browser.

The chart is about 260 lines (`ParetoChart.jsx`). `package.json` is unchanged.

### Algorithm (§10.4)

1. **Raster.** The buildable envelope is rasterised in the layout frame (u along the site's minimum-area rectangle): 2 m cells, 5 m above 50 ha gross (run settings). A cell is buildable only if the whole cell is inside the boundary, at least its edge's setback from every boundary edge (exact per-edge distance per cell), and touches no hard exclusion, so every placed block lies inside the envelope with no tolerance. Per cell the raster also keeps soft-exclusion membership, the height limit (lowest zone touched; the site limit unless wholly inside a zone) and the distance to the boundary.
2. **Order** (`PRIORITY`, the brief's list): data halls; substation; backup gensets and fuel storage; firm generation; BESS; ground heat rejection; wind; then ground solar fills what is left.
3. **Anchor costs** (lowest cost wins; ties: lower row, then column, then unrotated): first hall farthest from the POC, further halls next to placed halls; substation nearest the POC; gensets within 30 m of a hall, then farthest from receptors when there are any, else nearest the halls; fuel next to the gensets, then toward the access point; firm plant nearest the gas main when it burns gas, else farthest from receptors, else next to the substation; BESS next to the substation; ground heat rejection next to the halls (farthest from receptors when there are any); wind farthest from the boundary and halls.
4. **Rules.** For each block a forbidden mask is painted: outside the envelope, soft exclusions (except for solar where allowed), cells within the boundary separation, cells above the height limit, and the true rectangle of every placed block dilated by the required separation (the larger of the two clearance rings or a pairwise rule such as BESS-to-building 10 m or fuel-to-building 6 m). A vertical free-run array over the mask makes one row scan find every free position of a rectangle (the equivalent of an integral-image test); rows are visited in order of their cost lower bound and the scan stops when no row can beat the best.
5. **Relaxation** (soft rules only, `LAYOUT_LEVELS`): L0 default rules; L1 separations at their minimum values; L2 height limit exceeded; L3 both; L4 also soft exclusions. A block goes in at the first level that works; every rule it breaks at its position is recorded and named ("Fits with flags"). Hydrogen's 25 m hazardous-area separation is never relaxed; wind topple and noise buffers are flag-only.
6. **Land budget.** The roads/parking/landscaping allowance is held back as a budget, not a located area: a block that would take the placed land take above the net developable area is not placed.
7. **Unplaced tray.** A block with no position at L4 (or over budget) goes to the tray with its area; the option "Does not fit", and the flag names every unplaced block and the shortfall in m².
8. **Solar fill** (§10.4 "iteration with sizing"). Ground PV takes the remaining buildable cells with its 5 m clearance, leaving out strips under 10 m wide, within the remaining net budget. For "fill residual" options the ground PV MWp is then the filled area ÷ 1.2 ha/MWp (technology library; `applySolarFill`, before dispatch); for "fixed" PV a shortfall is unplaced area. No other sizing depends on the layout.
9. **Batch and cache.** Options with the same block-set key share one layout (T1: 2,000 options → 1,324 distinct layouts). The distinct sets are laid out as one batch sorted so shared leading blocks are placed once (a stack of placement states: the 1,324 T1 sets hold 30,299 blocks, but only 2,956 placement attempts run), with a memo of failed searches. Each result equals the single-set run (test 9d checks 31 sets). Deterministic: no randomness, fixed tie-breaks.
10. **Timing.** T1 layout stage 3.5 s single thread for 2,000 options (2.6 ms per distinct layout including the facts and site fit; §17 target ≤ 20 ms per option on a 15 ha site).

### Site-fit outputs (§10.6) and flags

- **Status**: "Does not fit" when any block (or fixed ground PV area) is unplaced; else "Fits with flags" when a rule was relaxed, a height limit is exceeded (height is soft in placement: an over-height block is placed and flagged), the roof is over-allocated, a wind buffer is not met, hydrogen or an SMR is present, off-site land falls short of what the option needs, or the noise proxy is above the threshold at a receptor; else "Fits".
- **Area budget bar** by energy source against the net developable area, with the not-placed part beyond 100 % hatched in the flag colour, and the same numbers as a table. **Land take** on site (all blocks + ground PV, placed or not) and off site; **shortfall** beyond 100 %; **residual** net area; **expansion headroom** = residual net area ÷ land take per MW IT of the IT-scaling blocks (an estimate; 0 when the option does not fit).
- **Height check** per zone (site limit and each zone): tallest element (building + roof zone, stacks, wind tip) and pass/exceeded.
- **Separation checklist**: each rule with its required, minimum and achieved distance and pass / relaxed / fail (a layout never breaks a minimum: test 9e), plus the genset-distance rule, the POC preference for the substation and the wind buffers.
- **Noise proxy**, labelled "screening proxy, not an acoustic assessment": Lp = Lw − 20·log10(r) − 8 (hemispherical spreading only); distance and level from each noisy block to the nearest receptor and to the boundary; receptor levels for normal operation and for standby gensets separately; flag above `requirements.noiseNightDbA` (45 dB(A) at night) at receptors only. The highest normal-operation level on the boundary is reported for information.
- **Roof use**: roof area split into plant, PV, edge setback and free (over-allocation flagged).
- **Flags** (§15 "Site fit"): `site-does-not-fit` (major), `site-relaxed`, `site-height`, `site-soft`, `site-genset-distance`, `site-wind-buffer`, `site-hydrogen`, `site-offsite-land`, `site-roof`, `site-noise` (minor), `site-soft-solar`, `site-smr` (info); `target-landtake` (Targets and ceilings, minor) when a land-take ceiling is set and exceeded. None of them carries `permitting: true`, so none enters deliverability (see judgement call 13).

1. `siteRank()` added; `markDominance()` now lets option j dominate option i only if j's site-fit status is at least as good as i's (as already done for resilience). 3. `SORTERS` gain `landTake` and `siteFit`, for the ranked list's new columns. View only.

**`sizing.js`**
1. The area budget reads the site model's gross area, buildable envelope (per-edge setbacks and hard exclusions) and net developable area when the run context has one (it always does in a run); the old rectangle formula remains for a context without a site model. Reason: §5.2 derived areas. For the T1/T3 area rectangle with a uniform setback the two give the same numbers, so the pre-layout estimate did not change.
2. The "fill residual" sizing sentence now reads "area-budget estimate before layout … (replaced by the layout fill, §10.4)". Reason: it is replaced by step 3.
3. Reason: §10.4 "'fill residual' solar sizing is computed after the other blocks are placed. No other sizing depends on layout." ### Energy-source colour system (§16) and the palette validator

The site blocks use the eight categorical hexes of the reference palette (light `#2a78d6 #eb6834 #1baf7a #eda100 #e87ba4 #008300 #6250d6 #e34948`, dark `#3987e5 #d95926 #199e70 #c98500 #d55181 #008300 #9085e9 #e66767`), assigned by convention: grid/substation blue, diesel gensets and their fuel store orange (fuel with a different hatch), gas red, BESS aqua, fuel cells green, solar yellow, nuclear magenta, hydrogen violet, wind the grid blue (with its own hatch). Data halls and heat-rejection plant are infrastructure, not energy sources, and use two neutrals (light `#d7d2c6` / `#a9a59b`, dark `#5a5e66` / `#80858d`). Validator (`validate_palette.js`, surfaces = the plan's envelope fill `#fbfaf6` light, `#2a2e34` dark):

- Eight hexes, adjacent pairs (the check for stacks and bars): **pass** in both modes (worst adjacent CVD ΔE 9.1 light / 8.4 dark, normal-vision 19.6 / 19.3). Contrast below 3:1 for aqua, yellow, magenta (light) and green (dark): relief = every block's ink outline, text label, hatch, legend and table.
- Eight hexes, `--pairs all` (the right check for a plan, where any two blocks can touch): **fail** in both modes (light: green–orange CVD ΔE 3.2, red–orange normal 7.1; dark: magenta–aqua CVD 1.6, red–orange 7.1). The reference says no ordering of eight colours passes all pairs; such forms cap at three colours or need composite encoding.
- First three slots (blue, orange, aqua) all pairs: pass. The most common trio on T1 plans, grid + diesel + gas (blue, orange, red): fail (orange–red normal ΔE 7.1).

Decisions: (1) colour is never the only carrier on the plan (§16 "site blocks have hatch patterns"): each source has its own hatch (gas 135° vs diesel 45° diagonals, fuel a plus grid, BESS a square grid, solar vertical, fuel cells dashes, heat rejection dots, hydrogen large dots, nuclear diagonal cross, wind rings), a short text label on every block large enough (Hall, Sub, Gen, Fuel, BESS, Eng, GT, FC, H₂, HR, WT), a legend, the tooltip and live text, and the table; (2) heat rejection was moved from violet to a neutral, which removes the worst frequent collapse (grid–heat rejection, blue–violet, CVD ΔE 1.9 dark, in 1,340 of 2,000 T1 plans); (3) re-assigning hues to maximise separation of the pairs that co-occur was evaluated over all 40,320 assignments: the best raises the co-occurrence-weighted pass rate from 73 % to 83 % but puts diesel in green and BESS in violet, so the conventional assignment was kept. With heat rejection neutral and the fuel store sharing the diesel hue, a T1 plan shows a median of 4 source hues (maximum 6; 595 of 2,000 plans show 3 or fewer) besides the two neutrals.

### Judgement calls (each also in `SITE-PROGRESS.md`)

1. Own geometry kernel instead of Turf/Clipper (offline single file, size); Greiner–Hormann with deterministic perturbation for degenerate cases.
2. Local equirectangular projection on WGS84 radii (M, N at the origin latitude), about the boundary centroid, or the project location for the area rectangle.
3. Offsets: mitre at convex vertices; arc at reflex vertices with equal setbacks (exact erosion); mitre at reflex vertices with unequal setbacks (conservative). The raster applies exact per-edge distances per cell.
4. The raster is conservative: a cell is buildable only if the whole square is inside the envelope and touches no hard exclusion. A cell takes the lowest height limit it touches, and the site limit unless it lies wholly inside a zone (zones override the site limit up or down).
5. Roads/parking/landscaping allowance = fraction × envelope (the brief defines it as a fraction of the net developable area, which is circular); net developable = envelope − allowance; enforced as a land budget in placement, not as a located area.
6. Default POC = the default access point (no road data offline, so "nearest boundary point to the nearest road" cannot be computed); default access = mid-point of the longest edge.
7. Exclusion type defaults: only flood zones are soft.
8. T2 fixture: T1 with 6 ha and a 15 m height limit. T4 fixture: 5 MW, 1 ha, grid 8 MW now and at full connection (date = start), one 5 MW phase at month 12.
9. Building: one block per phase, split above 25,000 m²; building clearance 6 m (fire access); first hall farthest from the POC, further halls next to placed halls.
10. Unit arrays: at most 12 units, 2 rows, 4,000 m² per array (engines and turbines get fewer units per array); double-deck = two units per position (half the footprint per unit, 12 m high); in-building gensets add a plant room to the halls.
11. The height limit is soft in placement (prefer compliant cells, else place and flag): an over-height block makes "Fits with flags", never "Does not fit". At the defaults (2 storeys × 6 m + 4 m roof zone = 16 m) every hall exceeds T2's 15 m limit.
12. Relaxation levels L0–L4 with a minimum value per rule (judgement); hydrogen's 25 m never relaxed; wind topple and noise buffers flag-only.
13. Noise proxy: hemispherical spreading only; normal operation and standby gensets reported separately; flag only at receptors (boundary level shown for information). The noise flag has category Permitting (§15) but `permitting: false`: it does not enter deliverability, because §5.7/§11 keep site fit out of the score by default and the proxy is not a permitting determination.
14. SMR off site by default (1 ha per 100 MWe); an SMR, hydrogen and an off-site land shortfall each give "Fits with flags".
15. Dominance includes site-fit status (§7.2 step 6).
16. The run keeps a compact site-fit summary per option; the plan and the §10.6 detail are recomputed on demand through `HOOKS.layout` (the same code path; 9d checks they agree).
17. Performance: batch layout with prefix sharing, failure memo, cost-bounded row/column search.
18. Site tab: the plan always shows the current site inputs, with blocks only when the run matches them (site key); layouts for the plan and the thumbnails are recomputed on demand and cached per run and option.
19. Typed coordinates are "lat, lon" per line with a decimal point. GeoJSON/KML import offers a "use as" choice per feature, pre-set from its name (first polygon = boundary); holes in an imported boundary become hard exclusions (type Other); an off-site polygon sets only the off-site area (not drawn).
20. A new boundary resets the per-edge setbacks (the edge count and order change).
21. Heat rejection and data halls draw in neutrals (see the palette section); hydrogen takes violet.
22. Option selector lists every option in rank order (no extra constant); the leader is shown unless another option is chosen (from the selector, a thumbnail, or "Show this option's layout" in the option detail).
23. The site-fit penalty points (10 for "Fits with flags", 25 for "Does not fit") are judgement; the penalty stays off by default.

### Open points

1. **Near-margin spatial failures.** 280 of the 1,014 T1 options that do not fit need less land than the net developable area: the conservative raster, separations and anchor heuristics leave no position for one block. The plan shows why; manual editing (stage 7) is the brief's remedy.
2. **Half of T1 does not fit on 15 ha at the default densities**: air cooling 457 of 513, evaporative 334 of 482, immersion 148 of 507, DLC 75 of 498. The building footprint follows the §5.3 density, gross-up and storeys defaults (indicative); worth checking with the client's building data before reading much into it.
3. **AC7 margin.** On T2 with C17 GIS and C18 double-deck included, 2 of the 2,000 sampled options (196,996 combinations) fit with flags (both DLC with a PPA hybrid; the halls exceed 15 m). Deterministic, so the test is stable, but thin; locking cooling to DLC gives more fitting options.
4. **§17 timing.** Auto-layout per option is well inside 20 ms. The whole T1 run is 9.4–11.8 s single thread in Node (layout 3.5 s, dispatch 5.2 s) against the 3.0 s screening target, which the core slice already missed (Brief issue 2); in headless Chromium on this 2-core sandbox the run takes 13 s on 1 worker. A site edit re-screens every option (fill-residual solar changes dispatch), so "site edit → all layouts ≤ 1.0 s" is not met either.
5. **Noise and stack-height flags vs deliverability** (judgement call 13): §15 lists "noise proxy above threshold" and "stack height above height limit" under Permitting, and §9.9 counts permitting flags in deliverability, while §5.7/§11 keep site fit out of the score unless the penalty is on. This build keeps both out of deliverability: the noise flag is category Permitting with `permitting: false` (it carries the note "Screening flag, not a permitting determination"), and a stack above the limit is part of the site-fit "Height limit exceeded" flag. Owner decision whether either should count.
6. **Palette**: plans fail the all-pairs colour checks, as any eight-colour palette would; identity relies on hatch, label, legend and table. Future dispatch stacks should stack sources in the palette's slot order to keep the adjacent-pair guarantee.
7. **Spatial library values in the UI.** The 87 spatial records are labelled in the registry and covered by test 5d, and the Site tab says every spatial default is indicative — unverified, but there is no per-value library page yet.
8. **Screen-reader walk-through** of the Site tab with NVDA + Firefox and VoiceOver + Safari (§17) not done; checked with axe, keyboard and the live-region text in headless Chromium.
9. **Large sites.** The 5 m raster above 50 ha (T5) is in place but T5 itself is not a fixture in this slice.
