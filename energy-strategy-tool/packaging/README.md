# Packaging: installable web app and desktop program

The owner chose **Windows and phone only** (2026-10-21):

| Form | How to get it | State |
|---|---|---|
| **Windows program** (Electron 44.9.0) | Download from GitHub (below) | Built on GitHub by the **Desktop builds** workflow |
| **Phone** | The private Claude artifact link "Concept Energy Optioneering", updated to the latest build | Opens in the phone's browser; private until shared |

The model is the same in every form: it runs entirely on the device, with no server, no account and no telemetry.

The installable web app (PWA) in `pwa/` is still built and tested by CI (12 checks) but is **not hosted**; the owner
chose the Claude link for the phone instead. macOS and Linux downloads are no longer built; `desktop/build-desktop.mjs`
can still make them (`--platforms darwin-arm64` etc.). A Linux build is made in CI only to launch-test the program.

## Get the Windows program

1. On GitHub, open **Actions → Desktop builds**, and open the latest run with a green tick (or press **Run workflow**).
2. Under **Artifacts**, download `desktop-win32-x64` (about 151 MB). You must be signed in to GitHub to download.
3. Unzip it (GitHub wraps it in a second zip: unzip both), open the folder and run
   `Concept Energy Optioneering.exe`. Keep the folder together; the program needs the files next to it.

**The program is not code-signed**, so the first launch shows "Windows protected your PC" (SmartScreen). Choose
*More info* → *Run anyway*. Signing needs a paid certificate and can be added to the workflow later without changing
the app.

## What the desktop program does and does not do

- Loads the bundled web app from `app://bundle/` in a sandboxed window: context isolation on, no Node.js in the page,
  a Content-Security-Policy that allows only the app's own inline scripts (by SHA-256 hash).
- Makes no network connection: no host name resolves inside the program and proxy settings are ignored, and every
  http, https, WebSocket and FTP request from the page is cancelled as well. Links to websites open in your normal
  browser. Checked by tracing every process of the program (D12): no DNS lookup and no connection off the computer
  during start-up and a model run.
- Asks where to save the run log (JSON or CSV), and accepts downloads only from the app itself.
- Remembers its window size and position. A second copy hands over to the one already open.
- Electron fuses: no "run as Node", no `NODE_OPTIONS`, no Node.js `--inspect`, app code only from `app.asar`.
  Chromium's own `--remote-debugging-port` switch still works (the desktop test uses it); like any program, it can be
  started with debugging by someone who can already run programs as you.
- Does **not** update itself, send anything, or need an internet connection.

## Build and test it yourself

Needs Node.js 22; the Linux test needs `xvfb` and Playwright.

```
cd ../app && npm ci && npm run build                     # the web app (input for both forms)
cd ../packaging && npm ci

npm run pwa && npm run test:pwa                           # PWA into out/pwa/, 12 checks (P1-P12)

node desktop/build-desktop.mjs --platforms linux-x64      # one or more of linux-x64, win32-x64, darwin-x64, darwin-arm64
npm run test:desktop                                      # 11 checks (D1-D11) on the Linux archive
```

Output goes to `out/` (not committed): `out/pwa/` and `out/desktop/` (archives, `SHA256SUMS.txt`,
`build-desktop.json`). Build one desktop platform at a time if disk is short: the script deletes each platform's
unpacked folder and Electron download once its archive is written. Icons are generated by `npm run icons` from
`icons/icon-art.mjs` and committed in `icons/generated/`.

The version in file names (`0.2.0-site`) is the model engine version read from the web app build.

## Tests

| Suite | Checks |
|---|---|
| `test:pwa` (P1–P12) | Loads and runs from a GitHub-Pages-like server; manifest and icons; maskable safe zone; service worker control; other pages on the same site left alone; offline reload and full run; installability; update notice (accessible, never forces a reload); works without service workers |
| `test:desktop` (D1–D12, on the Linux build) | Archive checksum and layout; bundled web app unmodified; fuses; window loads; full model run with no page errors; page requests refused; CSP blocks injected scripts; no Node.js in the page; navigation and pop-ups blocked; single instance; clean quit and saved window size; whole-program network trace with strace (no DNS lookup, no connection off the computer, proxy settings ignored) |

Latest results: `test-results/pwa.json`, `test-results/desktop.json`. Each test run rewrites them, so commit them together
with a verified change.

Not covered by a test: the run-log save dialog, restoring the window position (only the saved size is checked), and
the macOS and Windows builds' launch.

## Decisions

1. Input is the single-file build only; the hosted variant is for embedding in a host page and is not packaged.
2. Icon: a trade-off frontier with dominated options and the picked knee in amber on the app's accent blue
   (#1f5f8b / #ffb366), simplified at 16–32 px; maskable art scaled to 0.8 so the mark stays inside the safe zone.
3. PWA short name "Optioneering"; manifest id "concept-energy-optioneering", so the identity holds wherever it is hosted.
4. Theme colours follow the app's top bar in each theme, so an installed window's title bar blends in.
5. The service worker's version is a hash of the shell files; any change gives a new cache.
6. The service worker only handles this app's URLs and only deletes its own caches, because `slappy-69.github.io` is
   shared by every Pages site of the account. No `.nojekyll`.
7. Updates: the browser checks `sw.js` on each load, plus when the app becomes visible (at most once a minute) and
   hourly. The shell is cache-first, so one version is never mixed with another.
8. The update notice is a polite status message with Reload and Later; it never moves focus.
9. Service-worker registration is skipped where unsupported, and its failures never show the app's error box.
10. The GitHub workflow builds with the same script tested here (`desktop/build-desktop.mjs`), not electron-builder.
    Trade-off: no installers (NSIS, DMG, AppImage), only archives. electron-builder can be added if installers are wanted.
11. The Electron download runs in a child process with up to 3 attempts, because a dropped connection can crash the
    downloader outright.
12. The desktop test attaches over Chromium's remote-debugging port, since the disabled `--inspect` fuse rules out
    Playwright's Electron launcher.
13. Tests run as root pass `--no-sandbox`; the window's own sandbox and context isolation stay on (checked by D8).
14. macOS signatures are checked with `desktop/macho-verify.mjs` (ad hoc CodeDirectory present, every code page's
    SHA-256 matches the file), not `rcodesign verify`: version 0.29 of that command rejects every ad hoc signature
    ("CMS error: missing further values", since ad hoc signatures have no CMS blob). Every macOS build also runs a
    self-check of the checker: copies of the main executable with a changed header byte, a changed code byte and a
    corrupted signature must all fail, or the build stops. The checker does not cover the special slots (Info.plist,
    resources, requirements) or CodeDirectory fields outside the page hashes.
15. **No network at the Chromium level** (`host-resolver-rules=MAP * ~NOTFOUND`, `no-proxy-server`). An independent check
    traced the program at start-up and found DNS lookups for `redirector.gvt1.com`, where Electron fetches spell-check
    dictionaries, made before the session's spell checker could be switched off. The page-level blocks could not stop
    them. With the two switches, nothing resolves and no proxy is used; D12 traces every process to prove it.
16. Bundled weather stations (OPEN-QUESTIONS 114): `weather/weather-stations.json.gz` (from the latest full "Weather data" run, fetched by the Desktop builds workflow) is copied next to the page as `web/weather-stations.json.gz` and recorded in `build-info.json`. The page reads it from `app://bundle` (allowed by `connect-src 'self'`; no network). Without it the program uses the EPW upload or the synthetic profile. Check D5b.
17. Downloads are accepted only from the app's page: a `blob:` URL of the app's origin, or a `data:` URL started by an
    app page.

## Not done

- No code signing or notarisation (see above).
- The Windows build is produced on Linux and checked for structure and fuses, but it is not launch-tested
  automatically: the same app and settings are launch-tested on the Linux build (D1–D12), in CI and locally.
- The PWA is not hosted (owner's choice: the phone uses the private Claude link).
- The final Opus review of the packaging started on 2026-10-19 but stopped early at the weekly usage limit; it did not
  report. The Haiku check was done and answered (`../verification/packaging/H1-packaging.md`).
